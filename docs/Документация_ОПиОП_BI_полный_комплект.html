01. Описание проекта

1.1. Назначение

Дашборд ОПиОП BI — веб-приложение для визуального анализа калькуляции услуг по данным Excel.

Система:

  • загружает и проверяет Excel-файл с листом калькуляции;
  • строит витрины: классы → услуги → виды затрат (прямые / косвенные / неэффективность);
  • хранит историю загруженных версий файла;
  • позволяет редактировать активную книгу в браузере (Univer) и сохранять новую версию;
  • предоставляет health/readiness для мониторинга.

1.2. Границы системы

Входит в scope

  • Веб-UI дашборда и drill-down навигация.
  • API загрузки / выбора / скачивания Excel.
  • SQLite-реестр метаданных файлов.
  • Локальная сборка frontend (без внешних CDN в runtime).
  • Docker Compose: nginx (TLS) + FastAPI (internal).

Не входит в scope

  • Корпоративный SSO / LDAP / AD (есть только Basic Auth — временно).
  • Разграничение ролей (все авторизованные пользователи равны).
  • Аналитическое хранилище (DWH) — данные не нормализуются в витрину БД.
  • Высокая доступность и горизонтальное масштабирование (один инстанс, SQLite).
  • Обработка персональных данных (ПДн) — запрещена в базовом сценарии.

1.4. Технологический стек

Frontend Vite, Tailwind, Chart.js, ExcelJS, Univer

Хранение SQLite + файловая система (data/, uploads/, runtime/, logs/)
Контейнеризация Docker multi-stage (node:24-slim → python:3.12-slim), UID 10001

1.5. Ключевые свойства v1.2

  • Production: DEBUG=false, Basic Auth только через HTTPS, CSRF на POST.
  • Публикация только через nginx :80/:443; backend :8000 во внутренней Docker-сети.
  • OpenAPI/Swagger и /debug отключены в production.
  • Усиленная XLSX-валидация (ZIP/структура, лимиты, изолированный worker).
  • Security headers (CSP, HSTS, X-Frame-Options и др.), non-root контейнеры.
  • Frontend без runtime-CDN.
  • Backup/restore: scripts/ops/backup_restore.py.

2.4. Поток обработки запроса (просмотр дашборда)

1. nginx (TLS) → Basic Auth (если включён)
2. CSRF token в сессии (для последующих POST)
3. SessionMiddleware → active_file_id (или latest valid)
4. FileRegistry.path_for(record)
5. DashboardPayloadCache.get(file_id, path, loader)
6. Jinja2 TemplateResponse + security headers

2.5. Поток загрузки Excel

POST /api/files/upload (или /api/excel/save-version)
  → CSRF + Origin/Referer
  → rate limit (app + nginx)
  → запись в uploads/.incoming/{uuid}.xlsx
  → MAX_UPLOAD_BYTES / квоты
  → validate_excel_file() (worker + timeout)
  → move в uploads/{uuid}.xlsx
  → INSERT в SQLite (is_latest=1)
  → session.active_file_id = новый id
  → invalidate cache

2.6. Активный файл и сессии

  • Выбор файла хранится в signed cookie-сессии (active_file_id).
  • В production: Secure / https_only, SameSite=lax.
  • Выбор действует только для текущего браузера/сессии.
  • Глобальный «последний» файл (is_latest) обновляется при успешной загрузке.

03. Архитектура базы данных и хранилища

3.1. Общий принцип

Система не хранит аналитические факты в реляционной БД.

Что Где
Метаданные Excel-файлов SQLite (runtime/dashboard.sqlite3)
Содержимое Excel Файловая система (data/, uploads/)
Кеш дашборда Память процесса (не персистентно)
Логи logs/app.log, logs/errors.log

Это упрощает развёртывание (один контейнер), но ограничивает масштабирование и требует бэкапа файлов + SQLite вместе.

3.2. СУБД

Параметр Значение
Движок SQLite 3 (stdlib sqlite3)
Путь (default) runtime/dashboard.sqlite3
Путь (Docker) /app/runtime/dashboard.sqlite3
Env DATABASE_PATH / OPOP_DATABASE_PATH
Доступ Один writer (один инстанс приложения)

3.3. Схема таблицы files

CREATE TABLE IF NOT EXISTS files (
    id               INTEGER PRIMARY KEY AUTOINCREMENT,
    original_name    TEXT NOT NULL,   -- имя, которое видит пользователь
    stored_name      TEXT NOT NULL,   -- имя файла на диске
    sha256           TEXT NOT NULL,   -- хеш содержимого
    size             INTEGER NOT NULL,
    mtime            REAL NOT NULL,   -- mtime файла на диске
    uploaded_at      TEXT NOT NULL,   -- ISO UTC
    status           TEXT NOT NULL,   -- 'valid' и др.
    validation_error TEXT,            -- nullable
    is_latest        INTEGER NOT NULL DEFAULT 0,  -- 0/1
    source           TEXT NOT NULL DEFAULT 'upload' -- 'default' | 'upload'
);

CREATE INDEX IF NOT EXISTS idx_files_status ON files(status);
CREATE INDEX IF NOT EXISTS idx_files_latest ON files(is_latest);

Смысл полей

Поле Описание
original_name Исходное имя .xlsx от пользователя
stored_name Для upload: {uuid}.xlsx; для default — имя из ACTIVE_DEFAULT_FILE
sha256 Контрольная сумма содержимого
is_latest Флаг «последняя принятая валидная версия» (один актуальный latest)
source default — стартовый файл из data/; upload — загружен пользователем / из редактора

3.4. Файловое хранилище

opop_bi/
├── data/
│   └── data.xlsx              # файл по умолчанию (ACTIVE_DEFAULT_FILE)
├── uploads/
│   ├── .incoming/             # временные файлы во время upload
│   └── {uuid}.xlsx            # принятые версии
├── runtime/
│   └── dashboard.sqlite3      # метаданные
└── logs/
    ├── app.log
    └── errors.log

Docker volumes (compose)

Хост Контейнер
./data /app/data
./uploads /app/uploads
./runtime /app/runtime
./logs /app/logs

3.5. Жизненный цикл записи

  1. При старте: ensure_default_file() регистрирует data/data.xlsx, если есть.
  2. Upload: временный файл → валидация → финальный путь → INSERT + сброс старого is_latest.
  3. Выбор файла пользователем: меняется только cookie-сессия, не is_latest.
  4. Удаление старых файлов из UI не реализовано (рост uploads/ нужно контролировать административно).

3.6. Диаграмма сущностей (логическая)

┌─────────────────────────────┐
│ files (SQLite)              │
│  id PK                      │
│  original_name              │
│  stored_name ───────────────┼──► uploads/{stored_name}
│  sha256, size, mtime        │    или data/{stored_name}
│  status, is_latest, source  │
└─────────────────────────────┘

Session cookie
  active_file_id ──────────────► files.id (только для браузера)

Аналитическая модель (классы, услуги, суммы) не материализуется в БД — строится на лету из Excel.

3.7. Рекомендации по сопровождению БД

  • Бэкапить runtime/ и uploads/ + data/ атомарно (один архив).
  • Не запускать несколько реплик приложения на одну SQLite без внешней блокировки.
  • Периодически чистить старые uploads/*.xlsx, если диск ограничен.
  • Не коммитить *.sqlite3, data/, uploads/ в git (уже в .gitignore).

04. API и маршруты

4.1. Общие правила доступа

Условие Поведение
DEBUG=false + заданы AUTH_* Basic Auth на всех маршрутах, кроме публичных; только через HTTPS
Публичные (приложение) GET /health, GET /ready
Публичные через nginx /health, /ready доступны только из MONITORING_CIDR
CSRF Все изменяющие POST требуют заголовок X-CSRF-Token
DEBUG=true Auth не обязателен; доступны /debug и OpenAPI (только dev)
OpenAPI /api/docs, /api/redoc, /api/openapi.json — только при DEBUG=true

4.2. Публичные эндпоинты (мониторинг)

Метод Путь Ответ
GET /health {"status":"ok"} — liveness
GET /ready 200 / 503 — булевы флаги готовности (без путей и stacktrace)

4.3. JSON API (требуют auth в production)

Метод Путь Назначение
GET /api/files Список файлов, active/latest IDs, флаг новой версии
POST /api/session/active-file/{file_id} Выбрать активный файл для сессии (+ CSRF)
GET /api/excel/active Скачать активный .xlsx
POST /api/files/upload Загрузить новый Excel (multipart file, + CSRF)
POST /api/excel/save-version Сохранить версию из редактора (+ CSRF)

Ограничения upload:

  • только .xlsx;
  • MAX_UPLOAD_BYTES (по умолчанию 50 МБ) → HTTP 413;
  • квоты MAX_UPLOAD_FILES / MAX_UPLOAD_STORAGE_BYTES;
  • ZIP/XLSX validation, лимиты листов/строк, worker timeout;
  • UPLOAD_RATE_LIMIT_PER_MINUTE → HTTP 429;
  • nginx: отдельный rate limit на upload-эндпоинты, client_max_body_size 52m.

4.4. HTML-страницы дашборда

Метод Путь Описание

05. Модель данных Excel (калькуляция)

5.1. Входной формат

Параметр Требование
Расширение .xlsx
Лист Первый лист книги (в документации/ошибках — «Калькуляция»)
Заголовки Многоуровневые: строки заголовков индексы 2–3 (pandas header=[2,3])
Минимум колонок ≥ 25

Валидация (file_validation.py) отклоняет файл, если:

  • нет услуг;
  • нет классов;
  • отсутствуют группы детальных колонок прямых / косвенных / неэффективности.

5.2. Ключевые колонки (по индексу)

Индекс Назначение
0 № строки (фильтр числовых строк)
1 Класс услуги (class_name; пусто → «Без класса»)
2 Наименование услуги (service_name)
4 Итого прямых расходов
16 Косвенные «с неэффективностью» (база для разложения)
22–24 Три колонки неэффективности (суммируются)

Детальные статьи затрат определяются по совпадению верхнего уровня заголовка с группами «Прямые / Косвенные / Неэффективность».

5.3. Расчётные поля услуги

direct_cost       = колонка[4]
inefficiency_cost = sum(колонки[22..24])
indirect_cost     = колонка[16] - inefficiency_cost   # «чистые» косвенные
indirect_sum      = indirect_cost + inefficiency_cost
total_cost        = direct_cost + indirect_sum

Также формируются словари детализации:

  • direct_details
  • indirect_details
  • inefficiency_details

5.4. Виды затрат в UI

Ключ URL Название Поле суммы Цвет (UI)
direct Прямые расходы direct_cost #1f6f66
indirect Косвенные расходы indirect_cost #3e7cb1
ineff Неэффективность inefficiency_cost #d47d2f

5.5. Иерархия навигации

Обзор (/dashboard)
  ├─ Класс (/dashboard/class/{class})
  │    └─ Услуга (/dashboard/class/{class}/service/{service})
  │         └─ Статья затрат (.../cost/{cost_key})
  └─ Вид затрат (/dashboard/cost/{cost_key})
       └─ Класс в разрезе вида (.../cost/{cost_key}/class/{class})

Документация для проверки информационной безопасности

1. Общие сведения

1.1. Назначение системы

Внутреннее веб-приложение для анализа калькуляции услуг по Excel-файлам с листом «Калькуляция»: витрины по классам, услугам и видам затрат, загрузка версий файлов, выбор активного файла в сессии, браузерный просмотр и редактирование Excel.

1.2. Регulatory scope (область регулирования)

НПА Применимость Комментарий
ФЗ №149 «Об информации…» Да Общие требования к защите информации в ИС
ФЗ №152 «О персональных данных» Нет (базовый сценарий) Система предназначена для калькуляции услуг/затрат без ПДн
ФЗ №187 «О безопасности КИИ» Нет Система не классифицирована как объект КИИ
Указ №250 Нет Не относится к перечню организаций, обязанных по Указу

Важно: загрузка файлов с персональными или иными конфиденциальными данными запрещена без отдельного согласования СБ и пересмотра мер защиты (в т.ч. по 152-ФЗ).

1.3. Классификация обрабатываемой информации

  • Тип данных: служебная/операционная информация (калькуляция затрат, структура услуг).
  • Конфиденциальность: внутреннее использование, доступ ограничен VPN/корпоративной сетью + аутентификация.
  • ПДн: не обрабатываются в штатном режиме эксплуатации.

2. Архитектура и сетевая модель

2.1. Схема размещения (production)

[Пользователь / VPN]
        │ HTTPS :443
        ▼
┌─────────────────────────┐
│ nginx (opop_bi_nginx)   │  ← единственная точка публикации портов 80/443
│ TLS, HSTS, rate limits  │
└───────────┬─────────────┘
            │ HTTP web:8000 (Docker internal network)
            ▼
┌─────────────────────────┐
│ FastAPI (opop_bi_web)   │  ← порт 8000 НЕ публикуется на хост
│ non-root UID 10001      │
└───────────┬─────────────┘
            │ bind mounts
            ▼
   data/ uploads/ runtime/ logs/  (тома на хосте)

2.2. Порты и протоколы

№ Источник Назначение Протокол Порт Примечание
1 АРМ пользователя / VPN Reverse proxy TCP 443 HTTPS, Basic Auth
2 Reverse proxy Контейнер web TCP 8000 Только внутренняя Docker-сеть backend
3 АРМ администратора Сервер приложения TCP 22 SSH, администрирование ОС/Docker
4 Система мониторинга Reverse proxy TCP 443 /health, /ready — только из MONITORING_CIDR

Порт 8000/18000 не публикуется на интерфейсы хоста в production compose.

2.3. Доступ извне

  • Публичный доступ из Интернета: не предусмотрен.
  • Доступ: сотрудники компании через VPN/корпоративную сеть.
  • Исходящие подключения приложения во внешние сервисы: отсутствуют (статика и зависимости собраны локально, CDN не используются).

3. Аутентификация и управление доступом

3.1. Текущая модель

Элемент Реализация
Аутентификация HTTP Basic Auth (AUTH_USERNAME / AUTH_PASSWORD в .env)
Авторизация (RBAC) Не реализована — один общий аккаунт для всех пользователей
SSO / AD / LDAP Не используются (запланирован переход)
Сессии Signed cookie (SESSION_SECRET), SameSite=lax, Secure/https_only в production
CSRF Сессионный токен для всех POST (X-CSRF-Token)
Публичные маршруты без auth /health, /ready (на уровне приложения); на nginx — ограничены по IP для мониторинга

3.2. Матрица доступа (упрощённая)

Роль Дашборд (HTTPS) Загрузка / редактирование Excel Администрирование сервера
Пользователь ОПиОП чтение запись нет
Администратор ИТ чтение запись полный доступ (ОС, Docker, nginx, .env)

3.3. Требования к учётным данным

  • SESSION_SECRET — не менее 32 символов, криптостойкая случайная строка.
  • AUTH_PASSWORD — не менее 16 символов при DEBUG=false.
  • Секреты хранятся только в .env на сервере; файл не включается в Git.
  • Ротация секретов — по регламенту ИБ организации.

4. Реализованные меры защиты

4.1. Транспортная безопасность

  • TLS 1.2/1.3 на nginx (порт 443).
  • Принудительный редирект HTTP → HTTPS.
  • HSTS: max-age=31536000; includeSubDomains.
  • Basic Auth в production принимается только через HTTPS (блокировка на уровне приложения при scheme != https).

4.2. HTTP-заголовки безопасности

Заголовок Где Назначение
Strict-Transport-Security nginx HSTS
Content-Security-Policy приложение Ограничение источников скриптов/стилей
X-Frame-Options: DENY приложение Защита от clickjacking
X-Content-Type-Options: nosniff приложение MIME-sniffing
Referrer-Policy приложение Ограничение referrer
Cross-Origin-Opener-Policy приложение Изоляция контекста
Cache-Control: no-store приложение Для API и dashboard

4.3. Защита загрузки файлов

Контроль Параметр / реализация
Расширение только .xlsx
Размер файла MAX_UPLOAD_BYTES (по умолчанию 50 МБ)
ZIP/XLSX-структура проверка сигнатуры, обязательных частей OOXML
Zip bomb лимит записей архива, коэффициента сжатия, распакованного объёма
Листы / строки XLSX_MAX_SHEETS, XLSX_MAX_ROWS_PER_SHEET
Таймаут проверки изолированный worker-процесс, XLSX_VALIDATION_TIMEOUT_SECONDS
Rate limit (приложение) UPLOAD_RATE_LIMIT_PER_MINUTE (по IP клиента)
Rate limit (nginx) отдельная зона для upload-эндпоинтов
Квота хранилища MAX_UPLOAD_FILES, MAX_UPLOAD_STORAGE_BYTES
Имя на диске UUID (не пользовательское)

4.4. Защита от утечек

  • /ready возвращает только булевы флаги готовности, без путей и текстов исключений.
  • Ошибки 500 в UI — обобщённые, с request_id; детали только в логах.
  • Логи не содержат паролей и CSRF-токенов (маскирование в logging_config.py).

4.5. Контейнерная изоляция

Сервис UID read_only cap_drop Примечание
web 10001 да ALL tmpfs /tmp
nginx 101 да ALL tmpfs для cache/run/conf.d
init-permissions root (одноразово) — ALL + CHOWN chown томов перед стартом

Docker-сеть backend — internal: true (backend недоступен извне).

4.6. Host / proxy hardening

  • TrustedHostMiddleware — проверка заголовка Host (ALLOWED_HOSTS).
  • TRUSTED_PROXY_IPS — доверие заголовкам прокси только от nginx.
  • Client IP для rate limit — не берётся из подменяемого X-Forwarded-For напрямую.

9. Контрольные проверки для СБ

Краткий smoke-check после развёртывания:

  1. http://<host>/ → редирект на https://.
  2. https://<host>/dashboard без credentials → 401.
  3. https://<host>/dashboard с Basic Auth → 200, заголовок CSP присутствует.
  4. https://<host>/ready с рабочей станции пользователя → 403.
  5. https://<host>/ready из сети мониторинга → 200 или 503.
  6. Порт 8000 с хоста/сети → недоступен.
  7. POST без CSRF-токена → 403.
  8. Загрузка файла > 50 МБ → 413.
